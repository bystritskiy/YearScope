# YearScope

Локальный дашборд: сколько времени за год ушло на игры, сериалы, кино, книги и тренировки — на одном экране и в сумме.

## Запуск

```bash
cp .env.example .env   # вписать TMDB_API_KEY
npm start              # http://localhost:3010
```

Зависимостей нет — Node 26 умеет SQLite и TypeScript из коробки, `npm install` не нужен.

Разовая синхронизация без сервера, удобно для проверки источников:

```bash
npm run sync
```

В Docker:

```bash
docker compose up -d --build
```

## Развёрнуто на NAS

Живёт в `/volume1/docker/yearscope` на NAS_HOST, рядом с KoShelf. Открывается на **http://NAS_HOST:3011** — снаружи 3011, потому что 3010 на этом NAS занят `dawarich_app`; внутри контейнера сервис всегда слушает 3010. Порт меняется переменной `YEARSCOPE_PORT`.

Две вещи туда кладутся руками, их нет в репозитории: `.env` с ключами и выгрузка myshows в `data/imports/`. Оба лежат в томе `./data`, поэтому переживают пересоздание контейнера.

Обновление после изменений в коде:

```bash
docker compose up -d --build
```

## Источники

| Активность | Откуда | Детализация | Как берётся |
|---|---|---|---|
| 🎮 Игры | gowithme.club | по дням | `GET /api/player?name=…&period=year` → `byDay`, `topGames` |
| 🎬 Кино | Letterboxd | по дням | RSS + хронометраж из TMDB по `tmdb:movieId` |
| 📚 Книги | KoShelf (NAS_HOST:3003) | по дням | `GET /api/reading/calendar?month=…` за месяцы с данными |
| 📺 Сериалы | myshows | по дням | выгрузка профиля из `data/imports/*.xlsx` + `profile.Feed` |
| 🏃 Тренировки | intervals.icu | по дням | `GET /api/v1/athlete/{id}/activities?oldest=…&newest=…` |

### Почему именно так

**Letterboxd** закрыт Cloudflare, публичного API нет, а RSS отдаёт лишь ~50 последних записей. Поэтому просмотры **накапливаются**: каждая синхронизация дописывает новое в `entries` по `guid`, а выпавшее из ленты остаётся в базе. Дневной ряд пересобирается из накопленного, а не из ленты.

**Хронометраж фильмов** кэшируется в `film_runtime` навсегда — TMDB дёргается только за новыми id. Без `TMDB_API_KEY` время считается по средней длительности (115 мин) и помечается в интерфейсе как оценка.

**myshows** не отдаёт историю публично: `profile.Feed` возвращает 25 последних отметок и игнорирует пагинацию, а `profile.Episodes` требует авторизации. Поэтому история берётся из **выгрузки профиля**, а лента добирает отмеченное после неё. Обе половины называют сериал оригинальным названием и дают номер серии, так что ключ `сериал|s01e04` совпадает — эпизод из двух источников схлопывается в одну запись. Если между датой выгрузки и окном ленты образуется провал, сервис пишет об этом на экране и просит обновить выгрузку.

Выгрузка кладётся в `data/imports/` (берётся самый свежий `.xlsx`). Папка не в репозитории — это личные данные, и она примонтирована томом, так что переживает пересоздание контейнера.

**Тренировки берутся из intervals.icu, а не из Garmin.** С часов они туда прилетают сами, а доступ несравнимо проще: HTTP Basic, где логин — литерал `API_KEY`, а пароль — персональный ключ из Settings → Developer Settings. Ни OAuth, ни пароля от аккаунта, ключ отзывается в один клик. Весь год приезжает одним запросом.

Время считается по `moving_time` — он честнее для «сколько занимался». Но у силовых и йоги он часто нулевой, поэтому там берётся `elapsed_time`.

**gowithme** пересчитывает прошлое задним числом, поэтому дневной ряд за год заменяется целиком, а не дописывается.

**Часовой пояс** контейнера должен совпадать с KoShelf (`Europe/Warsaw`), иначе чтение разложится по соседним дням.

**KoShelf нужен по сети.** На NAS контейнер стоит рядом с ним и достаёт по `NAS_HOST:3003`. А вот из Docker Desktop на маке локальная сеть не видна вообще (любой порт LAN — refused), поэтому там книги синхронизируются только при запуске через `npm start`, без контейнера.

## Экраны

**Сводка** — итог за год, карточки по активностям, график по месяцам и оговорки о полноте данных.

**Журнал** — лента активностей по дням, сверху свежее, с фильтром по активности: что за фильм, какая серия, какая тренировка и сколько это заняло.

**Карточка активности** — открывается кликом по карточке в сводке: полный рейтинг за год (а не топ-4, как на сводке) и лента только по этой активности.

Детализация в ленте у источников разная, и это видно. Фильмы, серии, книги и тренировки лежат поштучно. А gowithme не отдаёт разбивку по играм за день в разрезе игрока — эндпоинт `/api/day` групповой и не фильтруется ни `group`, ни `scope`, ни `player`. Поэтому игры показываются одной дневной строкой из точного `byDay`, а не выдумываются задним числом.

## Модель данных

Источники отдают разную детализацию, и подгонять их под общий знаменатель — значит врать. Поэтому:

- `daily` / `monthly` — временные ряды; на чтении берётся тот, что доступен, а гранулярность видна в API;
- `entries` — то, у чего есть настоящая дата (просмотр фильма, серия);
- `highlights` — топы вроде «во что больше играл»: у таких элементов одной даты нет, и в дневной ряд они не попадают;
- `sync_state` — статус источника, включая `covers_from`: с какой даты у него вообще есть данные.

`covers_from` — не техническая деталь: если источник знает только полгода, это написано на экране рядом с итогом, а не подразумевается.

## API

| Метод | Назначение |
|---|---|
| `GET /api/summary?year=2026` | всё, что рисует сводку |
| `GET /api/journal?year=2026&source=myshows` | лента активностей по дням, сверху свежее |
| `GET /api/source?id=myshows&year=2026` | один источник: полный рейтинг и его лента |
| `POST /api/sync` | синхронизация вручную (идемпотентна: повторный вызов присоединяется к текущей) |
| `GET /api/health` | статус и признак идущей синхронизации |

Фоновая синхронизация — раз в `SYNC_INTERVAL_MINUTES` (по умолчанию 1440, то есть сутки) и один раз на старте. Отсчёт идёт от запуска сервиса, а не от полуночи: перезапустил в 15:00 — следующая синхронизация в 15:00 следующего дня.
